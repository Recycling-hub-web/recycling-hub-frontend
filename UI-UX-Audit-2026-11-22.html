Recycling Hub · Design review · 22 November 2026 · MYT

UI/UX audit of the current system

The green visual identity and shared application shell provide a useful foundation. The first priorities are trustworthy submission outcomes, accessible task controls and honest dashboard failure states. The operational portal needs authenticated visual validation before a full redesign decision.

Report only. No application implementation, account permissions or business records changed.

Scope, evidence and limitations

Method: inspected the current working tree, not the outdated README; ran the existing Next.js preview and existing Playwright Chromium in a fresh browser; inspected public routes at 1440 × 1000, with selected mobile checks at 390 × 844. Read shared UI, hooks, navigation, role guards and representative workflow components. The frontend contains both Pages Router public content and App Router authenticated areas. Existing uncommitted work is included in this snapshot and was preserved.

Evidence labels: “Visually verified” means observed in the local rendered browser. “Source verified” means the implementation directly establishes the behavior, but it was not reproduced against authenticated live data. “Conditional” examples identify a dependency or input that exposes a risk; they are not claimed production incidents. User impact and prioritization are design assessments, not measured conversion or task-completion results.

What works well and should be preserved

  • Current brand: recycling green (#008a3e), deep industrial green (#0a3d2e), pale green surfaces, restrained slate neutrals, the Recycling Hub wordmark, rounded cards and pill-shaped actions. Preserve these instead of reviving the README’s obsolete navy e-invoice identity.
  • Public first impression: clear household minimum, Klang Valley service context, business quotation distinction and strong primary pickup CTA. The two-path entry avoids forcing household visitors through a long business form.
  • Typography and spacing: Inter for UI/body content, Montserrat for prominent headings, generous readable public line lengths, consistent card borders and whitespace. The login form is focused, uncluttered and fits the inspected phone viewport.
  • Business request guidance: an explicit four-step model, review/edit sections, phone-scheduling explanation and a “What happens next” panel. Source includes step-heading focus management and reduced-motion-aware step scrolling.
  • Shared foundations: one DashboardLayout, role-driven navigation, reusable page containers, status badges, cards, chart frame, table states and pagination. Improve these foundations before redesigning each module independently.
  • Modal foundation: shared Modal already includes a dialog role, accessible title, focus trapping/restoration, Escape behavior, body scroll locking and a scrollable body with fixed header/footer. Retain these behaviors while correcting the controls inside.
  • Mobile direction: source includes role-specific bottom navigation, an all-sections dialog, safe-area spacing, stacked record cards, larger system controls and mobile modal sheets. Preserve the intent, then verify with real role sessions.
  • Permission recovery: the access-denied screen offers a route back to the current user’s own dashboard; management controls are role-conditioned and finance displays reasons for reimbursement blockers. These are useful patterns, not proof that every permission path is correct.

01 · Certificate requests can disappear behind a success message

/track-trace

What is wrong
The submit handler validates two fields and sets submitted=true. It makes no API call and stores or routes nothing. The source explicitly describes this as simulated success.
User impact
A customer can believe a collection status or destruction certificate request reached the team and wait indefinitely. This breaks the core promise of the page.
Recommended improvement
Until a real request channel exists, replace submission with an explicitly labelled email or WhatsApp handoff. For the complete flow, persist a ticket, acknowledge only after server acceptance, and show a reference plus the actual follow-up channel.
Done when
A successful state requires a durable request ID or clearly says that the visitor must send the message in the external app. A failed request retains every field.

02 · Quote confirmation precedes the actual WhatsApp message

/request-quote

What is wrong
The handler calls setSubmitted(true) before navigating to wa.me. Opening a composed message is treated as submission even though the visitor may cancel or lack WhatsApp.
User impact
The visitor can assume the business quote was delivered when no message was sent; navigating out also interrupts the website flow.
Recommended improvement
Label the action “Continue in WhatsApp”. State that the visitor must press Send there. Keep a copyable message and email alternative. Only say “Request received” after an application-owned backend acknowledges receipt.
Done when
Cancelling the WhatsApp handoff does not leave a false received/sent confirmation; a copy or alternate channel is available.

03 · Financial dashboard failures look like real zero balances

Accounting overview; driver overview charts

What is wrong
useAccountingOverviewStats catches errors by restoring zero-valued INITIAL data, then sets loading=false. Its status counts remain null, so the chart keeps loading. The driver aggregate request also swallows errors and leaves null chart data.
User impact
Accounting may interpret unavailable information as RM0 owed; drivers cannot distinguish a slow request from a failed one. The shared chart already supports errors, but these callers do not supply them.
Recommended improvement
Return explicit loading, success, empty and error states from the hooks. Show “Could not load” with Retry instead of money values on failure. Preserve the last successful values with an “Out of date” label when appropriate; pass errors into ChartFrame.
Done when
A failed aggregate request never renders a fresh zero total or an indefinite skeleton; retry can recover the affected panel independently.

04 · Read-only finance rows have no keyboard route to detail

Finance records across accounting, driver, staff and admin roles

What is wrong
FinanceRecordTable opens details from a mouse onClick on tr. The requester is plain text, and there is no normal details link. Driver rows have no per-row management action at all.
User impact
A keyboard user cannot open a driver finance detail record. Management users can reach reimbursement but still cannot use a standard link to inspect the record first.
Recommended improvement

05 · Proof uploads cannot be reached using the keyboard

StatusFileUpload in Collect, Reimburse and claim-payment modals

06 · Collection-point toggles are mouse-only

ToggleInput; collection-point create/edit forms

What is wrong
ToggleInput toggles state from an onClick on a label and renders the switch as div elements. There is no input, button, role or tab stop. The generic caption says “Click to toggle configuration”.
User impact
A keyboard or screen-reader user cannot reliably identify the setting, hear its state or change it.

07 · Text and primary-button contrast need stronger tokens

ReusableHero, footer, shared primary buttons, login

What is wrong
The hero accent and small supporting text use slate-400 (#94a3b8), which is 2.56:1 against white. The primary button uses white normal-size text on brand-600 (#008a3e), approximately 4.46:1, just below 4.5:1. These ratios use the configured solid colours, not antialiased screenshot pixels.
User impact
Essential words such as “Pickup” or “Certificate or Status” are less readable, and small supporting text and primary labels are harder to read in glare or with low vision.
Recommended improvement
Use slate-600/700 for meaningful secondary text and brand-700 for white-text action backgrounds, or introduce a compliant semantic action token within the existing green palette. Keep lighter tints for decoration and genuinely disabled content.
Done when
Normal text meets 4.5:1 and large text 3:1 in default, hover and focus states; review disabled content separately.

Evidence: components/ui/hero/ReusableHero.tsx · components/ui/buttons/Button.tsx · components/layout/Footer.tsx · ../tailwind.config.js

12 · Validation rules and error presentation have two competing owners

ValidatedForm + business pickup form + InputField

What is wrong
An empty Continue action produces the generic banner “Full name: This field is required.” and a green focused input, because submit capture intercepts the form before step-level validation runs. On-blur/domain errors use separate inline paragraphs and styles.

13 · Inline field errors are not programmatically connected

InputField, PasswordField, PhoneInputField and shared controls

What is wrong
Field-level errors render as paragraphs without stable IDs or aria-describedby links. InputField and PasswordField do not derive aria-invalid from their errors props. ValidatedForm adds it for native submit failures, but that does not cover every domain/API error path.
User impact
Screen-reader users can focus an invalid field without hearing why it failed or how to correct it.
Recommended improvement
Create a shared FieldShell with label, optional hint, error ID, aria-describedby and aria-invalid. Pass those attributes into every native/custom control and keep the error summary as an additional navigation aid.
Done when
Each invalid field announces its label, invalid status and exact correction message after client validation and server rejection.

17 · Pagination can override the server total with a partial page

TablePagination

What is wrong
When itemCount < itemsPerPage, displayTotal is calculated from the current page length instead of totalCount. The component also renders a range while loading, even when itemCount is zero.
User impact
If a partial response arrives with a larger server count, Next can be disabled prematurely. Example: page 1, 12 per page, 8 items and totalCount=40 becomes “of 8 / Page 1 of 1”. This is a component-level example; no live dataset reproduced it.
Recommended improvement
Treat the server count/next-page metadata as authoritative; clamp and refetch an invalid page after deletion/filtering. Hide the range or show a skeleton during loading and render a coherent zero-results state.
Done when
Server totals remain stable for partial pages; zero, loading, deleted-last-row and changed-filter scenarios never show impossible ranges or trap the user.

Evidence: components/ui/table/TablePagination.tsx
