What works well and should be preserved

  • Brand and hierarchy: recognizable green identity, white cards, neutral surfaces, restrained text hierarchy and consistent pill actions. Keep current logo, green tokens, typography family and status badge vocabulary.
  • Desktop shell: grouped sidebar sections, clear active state and persistent task context. Long-form details have useful overview/orders/documents/activity separation.
  • Mobile shell: role-specific main-work tab, large bottom navigation and a native workspace dialog. Escape closes it and restores focus to Menu. No document-wide horizontal overflow appeared in the inspected 390px screens.
  • Responsive lists: desktop tables become readable cards with labels on phones. Preserve this approach, and replace its text-based heuristics rather than rebuilding the presentation.
  • Recent functional improvements: all 69 mocked UI regressions passed, covering finance/claims permissions and retries, driver scheduling/local-time conversion, proof-upload guards, route limits and pickup detail keyboard links. Keep these checks as regression protection.
  • Form foundations: clear required marks, Malaysian phone support, retained values, step labels, localized validation messages and shared controls. Improve the validation contract rather than replacing forms wholesale.
  • Honest handoffs: the public quote/certificate/contact checks retain drafts and provide fallbacks rather than claiming an external message was delivered. Preserve that wording.

01. Failed delivery queue becomes a real zero

Affected area
Receiving overview: /receiving
What is wrong
With the delivered-orders API returning 503, “Awaiting close” displays 0. The preview section disappears because deliveries.length is zero and loading has ended.
User impact
The receiving officer can conclude there is no work even though the system cannot establish the queue size.
Recommendation
Pass the queue error into the metric card, show “Unavailable” and Retry, and keep the queue error visible independently of its item count. Preserve the last successful count only when clearly marked stale.
Acceptance check
A failed first load never displays a successful zero; retry recovers both count and preview.

02. Dashboard aggregates can load forever after failure

03. Mobile request actions open outside the viewport

Affected area
Request details → Actions; shared ActionsDropdown
What is wrong
At 390px, the 208px menu starts at approximately −80px. Edit, Create order and Cancel request labels are cut off. The menu aligns its right edge to a left-aligned trigger without clamping to the viewport.
User impact
Important request actions become hard to identify and operate on a phone.
Recommendation
Clamp the menu to a 12–16px viewport gutter, flip horizontal alignment near the left edge and limit height when space is short. Preserve desktop styling and the portal that prevents table clipping.
Acceptance check
All menu items remain fully visible at 320, 390 and 768px, including after scrolling.

04. Menu semantics promise keyboard behavior that is missing

Affected area
Shared ActionsDropdown
What is wrong
Opening Actions with Enter and pressing ArrowDown leaves focus on the trigger. The panel declares role="menu" and items declare role="menuitem", but there is no arrow-key navigation or initial item focus.
User impact
Keyboard and assistive-technology users encounter an unfamiliar, inefficient control.
Recommendation
Implement initial focus, ArrowUp/Down, Home/End and Escape focus restoration; alternatively use a disclosure of ordinary buttons with matching semantics. Avoid mixing the two patterns.
Acceptance check
Keyboard users can enter, traverse, activate and dismiss the menu; closing consistently restores trigger focus.

Assumptions and follow-up research

  • Fleet scale: vehicle-search priority assumes regular use across more than one page. Measure actual fleet size and lookup frequency; reduce priority for a permanently tiny fleet.
  • Receiving evidence: the missing inspection path is verified, but which proof, discrepancies and override reasons must be mandatory is an operations decision. Observe a receiving officer reconciling a real delivery before finalizing that redesign.
  • Category scale: the off-page parent problem is reproducible with fixtures; production may currently have all categories on one page. The data contract still fails as the taxonomy grows or is filtered.
  • Permissions: UI inconsistencies are verified against the frontend’s own capability rule. This report does not claim a backend authorization bypass. Actual server role enforcement needs separate integration testing.
  • Accessibility: observed semantics and keyboard issues warrant fixes, but no full conformance claim is made. Run NVDA/VoiceOver, 200–400% zoom, physical phone keyboard and high-contrast checks before release. Existing contrast tests cover selected controls, not the complete system.
  • Performance: no representative production latency, device CPU, long list or real upload measurement was performed. Do not interpret local fixture speed as production performance.
